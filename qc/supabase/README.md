# FQMS — Supabase Database

Schema for the **Food Quality Management System** (Nata de Coco / Tapioca Pearl
QC). This is an **independent system** — it shares no database, accounts, or
deployment with FAMMS. It only reuses code patterns.

## Run order

Execute in the Supabase SQL editor (or `psql`) in this exact order:

| # | File | What it does |
|---|---|---|
| 1 | `schema.sql` | All tables, indexes, triggers, auto-numbering functions |
| 2 | `rls.sql` | Enables RLS on every table + role policies |
| 3 | `seed_test_items.sql` | Demo factory, 7 inspection stages, ~55 test items |
| 4 | `migration_gudang_link.sql` | Additive: `batches.gudang_meta`, `ncr_records.machine_code` (Gudang One lookup/status-sync link — see below) |

```bash
# psql example
psql "$DATABASE_URL" -f schema.sql
psql "$DATABASE_URL" -f rls.sql
psql "$DATABASE_URL" -f seed_test_items.sql
psql "$DATABASE_URL" -f migration_gudang_link.sql
```

Migration files after `schema.sql` follow the naming pattern `migration_*.sql` and
are always additive (`ADD COLUMN IF NOT EXISTS`) so they're safe to re-run and
never require dropping the database — verified idempotent on a throwaway
PostgreSQL 16 instance.

`schema.sql` and `seed_test_items.sql` are idempotent-friendly (seed uses
`ON CONFLICT DO NOTHING`; re-running `schema.sql` will error on existing objects
— drop the schema or use a fresh database to re-apply).

## What gets created

- **20 tables** — 19 domain tables + `qc_doc_counters` (numbering helper).
  - Master data: `factories`, `profiles`, `customers`, `products`, `suppliers`,
    `test_items`, `inspection_stages`, `product_specs`, `inspection_templates`,
    `template_items`, `reference_documents`, `instruments`.
  - Execution: `batches`, `inspections`, `inspection_results`, `ncr_records`,
    `supplier_returns`, `customer_complaints`, `export_logs`.
- **~50 RLS policies** across 4 roles (`inspector` / `supervisor` / `manager` /
  `admin`).
- **Seed**: 1 factory, 7 stages, ~55 tri-lingual test items (sensory, physical,
  chemical, micro, packaging, water, environment, hygiene).

## Design notes / things to know

### Enum handling
All enum-like columns are `text + CHECK`, **not** Postgres `enum` types. This
lets QC supervisors' future values be added with a one-line `ALTER ... CHECK`
instead of the locking `ALTER TYPE ... ADD VALUE` dance. Keep new values in sync
with the app's TypeScript union types.

### Auto-numbering & concurrency
Document numbers are generated by `BEFORE INSERT` triggers calling
`qc_next_seq(prefix, date)`:

- `inspections.inspection_no` → `QC-YYYYMMDD-NNN` (3 digits)
- `ncr_records.ncr_no` → `NCR-YYYYMMDD-NN`
- `supplier_returns.return_no` → `RET-YYYYMMDD-NN`
- `customer_complaints.complaint_no` → `CMP-YYYYMMDD-NN`

`qc_next_seq` uses a single atomic `INSERT ... ON CONFLICT DO UPDATE ...
RETURNING` against `qc_doc_counters`, keyed on `(doc_type, seq_date)`. That
statement takes a row lock on the counter row, so **two concurrent inserts can
never receive the same number** — the second transaction blocks until the first
commits, then reads the incremented value. A rolled-back transaction can leave a
gap in the sequence; this is acceptable for human-readable document numbers. If
you pass an explicit `*_no`, the trigger leaves it untouched (useful for
back-filling historical paper records).

### `profiles` and auth
`profiles.id` is intended to equal `auth.users.id`. The FK to `auth.users` is
**not** declared here to keep the schema portable/testable without the Supabase
auth schema. In the real project add:

```sql
alter table profiles
  add constraint profiles_id_fkey
  foreign key (id) references auth.users(id) on delete cascade;
```

and an `on_auth_user_created` trigger to auto-insert a `profiles` row on signup
(mirroring FAMMS). `pin_code` supports the shared-tablet fast user switch;
`preferred_language` defaults to `id` (Bahasa) for inspectors.

### Spec resolution & versioning (compliance core)
- `product_specs.customer_id NULL` = generic spec; non-null = customer-specific
  override. App resolves **customer-specific → generic**.
- Specs are versioned (`version`, `effective_from`, `effective_to`). The
  currently-effective row has `effective_to IS NULL` (partial index
  `idx_specs_effective` accelerates this lookup). Never mutate an old spec —
  close it (`effective_to = date`) and insert a new version.
- Each `inspection_results` row stores `spec_id`, **locking** the exact spec
  version used to judge it. This is the BPOM-audit guarantee: old records always
  reflect the standard in force when they were taken.

### Multi-sample & multi-source (future-proofing sockets)
- `inspection_results.sample_values` (JSONB array) stores every per-sample raw
  reading (e.g. `[12.1, 12.3, 11.8]`). `value_numeric` holds the representative
  value (average). `product_specs.judgment_mode` = `average` | `each_sample`.
- `inspection_results.entry_source` (`manual` / `excel_import` / `instrument` /
  `lab_import` / `api`) + `source_ref` (JSONB) are the universal result-intake
  socket. Phase 1 writes only `manual`; later sources need no schema change.

### Gudang One (warehouse app) link — `migration_gudang_link.sql`
- `batches.gudang_ref` (in `schema.sql`) already held a free-text warehouse
  reference. The migration adds `batches.gudang_meta` (JSONB) for the
  structured `{gudang_batch_id, lot_no, warehouse}` set when a batch is pulled
  via the "Ambil dari Gudang" lookup — the app checks this field to know
  whether a `qc-status` push-back applies to a given batch.
- `ncr_records.machine_code` (text, optional) records a suspected-equipment
  code on a quality issue, collected now for a future one-click FAMMS
  work-order link (Phase 2) — not otherwise used in Phase 1.
- Neither column is read/written by RLS policies or triggers; they're inert
  until the app's Gudang integration code (see project handoff doc) uses them.

### RLS summary
- **inspector**: reads master data + records; inserts/updates **own**
  `inspections` and their `inspection_results` only while status is
  `draft`/`partial`; can create `batches`; **cannot delete**, **cannot export**.
- **supervisor+**: full read/write, review/sign-off, master-data maintenance,
  batch status changes, NCR creation, supplier returns & complaints, exports.
- **manager+**: additionally the only role that can update **CCP-linked NCRs**
  (`is_ccp = true`) — enforced with a `WITH CHECK` split so a supervisor cannot
  set a CCP disposition (HACCP rule). Also NCR delete.
- **admin**: manages `factories` and `profiles` (users).
- **export_logs**: insert restricted to supervisor+ (and `exported_by =
  auth.uid()`); no update/delete policies → the audit trail is immutable.

Helper functions: `qc_user_role()`, `qc_is_supervisor_up()`,
`qc_is_manager_up()`, `qc_is_admin()` (all `SECURITY DEFINER`, so a user can read
their own role even under RLS).

### Storage buckets (create manually in the real project)
Not created by these scripts. Suggested:

```sql
insert into storage.buckets (id, name, public) values ('qc-photos','qc-photos', true);
insert into storage.buckets (id, name, public) values ('qc-documents','qc-documents', false);
```

`inspection_results.photo_urls`, `*.photos`, and `reference_documents.file_url`
point into these buckets.
